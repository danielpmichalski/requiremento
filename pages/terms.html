This page shows and edits terms.json, which specky.json names in your project. Opened directly from disk, the browser can't read that file by itself, so pick it once. Started with specky serve, the page loads it for you.

Your browser can't save files directly. You can read and edit here, then download the result and replace terms.json. Chrome and Edge save directly.

About this page: the ubiquitous language of the project

These terms are the ubiquitous language of the project, in the sense of Domain-Driven Design (Eric Evans): one shared vocabulary that product owners, stakeholders, developers and testers all use in the same way, in conversations, requirements, acceptance criteria, test cases, the user manual, the UI and the code. If a word means one thing in a meeting, another in a spec and a third in the code, bugs follow.

How to use the terms

  • Look terms up here first. A requirements document may narrow a term for one story in its own "Terms" section, but it links the term here (terms.html#loan-period) and must not contradict it.
  • One concept, one term. Don't use the synonyms marked avoid in new text.
  • UI labels are separate. UI is the text users see (possibly in another language). Specs and the user manual quote it ("Renew loan"); everywhere else, use the term.
  • Code names should match. If the code name differs from the term, rename it when you touch the code. The code links to the term (terms.html#loan-period), not the other way round: terms don't list code names, which change more often than the terms.
  • Undecided meaning goes to Open questions, not into a definition.

How to maintain them

  • Keep the terms current as part of normal work: the story, spec or merge request that introduces, changes or retires a concept updates the terms in the same change.
  • When a requirements document defines a term other stories will need, move it here and link it.
  • Don't delete terms that were in use; retire them with what replaced them, so old tickets stay readable.
  • Review the whole list at least once per release and before a larger requirements analysis.
  • Write short, plain definitions, built from other terms where possible. Link a term with [[term-id]]; it shows the term's current name. Write code as `Name`.

How to edit

The data is the terms file of your project (schema: terms.schema.json). People edit it on this page: every change adds a changelog entry, and Save writes the file directly (Chrome or Edge). Agents and scripts edit the JSON directly, add a changelog entry themselves, and run specky check. Commit the file like any other source.

Open questions

Conflicts and unclear meaning. Resolve each with the PO, then fix the definitions and the documents involved.
